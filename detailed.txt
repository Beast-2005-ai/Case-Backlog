1. SYSTEM ARCHITECTURE & END-TO-END DATA FLOW
================================================================================

CaseTriage is built as a modular, decoupled system with three major services 
running in harmony:
1. React Frontend (Vite/TypeScript Dashboard)
2. FastAPI REST API Bridge (api_bridge.py)
3. Background Watchdog Orchestrator (watchdog-orchestrator.py)

Here is how the data flows through the system, from ingestion to prioritization:

[ Ingestion ]
    │
    ▼ (Direct UI File Upload or Manual JSON File Drop)
[ api_bridge.py ] 
    │ Checks: File size validation (min 20 words), Duplicate check (MD5/exact summary)
    ├─► Analyzes text for geographical indicators ("IPC" -> India, "SCOTUS" -> US)
    ├─► Detects legal domain ("divorce" -> Family, "murder" -> Criminal)
    └─► Generates standardized JSON + routes to pending_cases_json/<Region>/
    │
[ watchdog-orchestrator.py ] (Recursively monitors pending_cases_json/)
    │ Wakes up on file creation -> triggers judge.py
    ▼
[ judge.py ]
    ├─► SentenceTransformers embeds case summary (384-dimensional vector)
    ├─► Queries ChromaDB Vector Database for closest precedent (returns n_results=2)
    │     └─► Self-excluding check: skips first match if similarity distance < 0.05
    ├─► Rule Engine: Scores heuristics (Base 25.0, Case Type, Keyword matches)
    ├─► ML Engine: Extracts 5-dim features -> Runs XGBoost Regressor model
    ├─► SHAP Explainer: Computes Shapley values for feature contribution
    ├─► Deterministic Jitter: Hashes case ID + summary length to add micro-decimals
    └─► Appends computed data (Score, SHAP XAI, Precedents) to master_queue.txt
    │
[ React Dashboard ] (Polls api_bridge.py every 3 seconds)
    ├─► Fetches master_queue.txt contents
    ├─► Recharts renders live histograms, category doughnuts, and keyword radars
    └─► Clicking case slides open details containing SHAP waterfall and precedent info

2. THE MACHINE LEARNING PIPELINE: FEATURE ENGINEERING & XGBOOST
================================================================================

A machine learning model cannot process raw text directly. It requires numbers. 
Our feature engineering pipeline (defined in feature_engineering.py) transforms 
each legal case docket into a 5-dimensional numerical array.

The 5 Engineered Features:
---------------------------
- Feature 0 [Criminal Base]: Binary (1 if the case category contains "criminal", 
  else 0). This acts as a categorical structural indicator.
- Feature 1 [Family Base]: Binary (1 if the case category contains "family", 
  else 0).
- Feature 2 [Keyword Density]: A continuous numerical value representing the 
  sum of active weights of keywords matched in the text (capped at 32.0 points 
  to prevent keyword stuffing exploits).
- Feature 3 [Precedent Similarity]: Continuous numerical similarity calculated 
  from ChromaDB's cosine distance output: (1.0 - Cosine Distance). If no 
  precedents exist, defaults to 0.0.
- Feature 4 [Text Complexity]: Continuous numerical value of the lowercase 
  text character count.

Why XGBoost is Used:
--------------------
XGBoost (eXtreme Gradient Boosting) is a highly efficient implementation of 
gradient boosted decision trees. In this project, we employ an XGBRegressor 
which predicts a continuous priority score from 1.0 to 100.0.

1. High Tabular Efficiency: Our features are structured, tabular data. Tree-based 
   algorithms excel on tabular data, significantly outperforming deep neural networks.
2. Gradient Boosting Optimization: Instead of training independent trees (like 
   Random Forest), XGBoost builds trees sequentially. Each new tree is trained 
   to correct the residual errors made by the previous trees using gradient 
   descent on the loss function.
3. Regularization: XGBoost includes built-in L1 (Lasso) and L2 (Ridge) 
   regularization, preventing the model from overfitting to small training sets.
4. Handling Non-linear Relationships: It easily handles non-linear thresholds, 
   such as how text length (Complexity) or keyword weights interact together.

3. SERIALIZATION & MODEL STORAGE: HOW THE .PKL FILE IS GENERATED
================================================================================

The trained XGBoost model is serialized (saved) as a file named 
priority_model.pkl. This happens during the execution of train-model.py.

Step-by-Step Generation of the .pkl File:
------------------------------------------
1. Bootstrapping Target Labels: The training script loops through all historical 
   JSON dockets stored in the pending_cases_json/ folders. For each docket, it 
   runs the rule_engine.py to compute a baseline heuristic priority score. This 
   score serves as the ground-truth target label (y).
2. Creating Input Matrices: For each case, it extracts the 5 features using 
   feature_engineering.py to form the input feature matrix (X).
3. Fitting the Model: The XGBoost regressor is initialized with n_estimators=100 
   and max_depth=5. The model is fitted using model.fit(X, y). The algorithm 
   builds decision trees to minimize the Mean Squared Error (MSE) between its 
   predictions and the target scores.
4. Serializing with Joblib: Once training completes, the model is serialized using:
   `joblib.dump(model, "priority_model.pkl")`

What is a .pkl File?
--------------------
A `.pkl` file is a binary file format created by Python's serialization library 
(either `pickle` or `joblib`). Serialization is the process of converting a 
live Python object structure (including its weights, tree splits, and internal 
parameters) into a byte stream that can be saved to disk. When the system boots 
up, `joblib.load("priority_model.pkl")` reads this byte stream and instantiates 
the fully trained, ready-to-predict XGBoost model in memory within milliseconds.

*Note: We use joblib instead of standard pickle because joblib is optimized for 
objects containing large numpy arrays and complex numerical matrices, which is 
typical for ML models.*

Key Comparisons:
----------------
- vs. Linear Regression: Linear models assume features add up independently. However, 
  in law, features interact. (e.g., if Precedent Similarity is very high AND case type 
  is Criminal, the priority should jump exponentially, not linearly). Linear 
  models fail to capture these cross-interactions, leading to high bias.
- vs. Deep Learning (Transformers/BERT): While a Transformer model could read 
  raw text directly, it requires immense GPU resources, has high latency 
  (seconds per case), and consumes gigabytes of RAM. XGBoost processes cases 
  in milliseconds, runs comfortably on a single CPU, and has a memory footprint 
  of less than 15MB, making local edge deployment cost-effective.
- vs. Random Forest: Random Forests build trees independently and average their 
  predictions (bagging). XGBoost builds trees sequentially to minimize residuals 
  (boosting). XGBoost almost always achieves higher accuracy and a smaller 
  memory footprint than Random Forest, while integrating natively with SHAP 
  using optimized `TreeExplainer` algorithms.

5. BACKEND FRAMEWORK: WHY FASTAPI WAS CHOSEN OVER FLASK AND OTHERS
================================================================================

FastAPI was selected as the backend API bridge for CaseTriage. Here is why:

1. Asynchronous Execution (ASGI):
   Unlike Flask, which is built on the older, synchronous WSGI standard, FastAPI 
   is an ASGI (Asynchronous Server Gateway Interface) framework. It handles 
   requests concurrently using Python's `async` and `await` keywords. During 
   heavy case ingestion, incoming requests (e.g. file uploads, log fetching) 
   do not block the main thread. This allows the API to serve hundreds of 
   concurrent connections without bottlenecking.
2. Built-in Data Validation (Pydantic):
   FastAPI uses Pydantic for data parsing and validation. When the admin saves a 
   configuration payload (`/config`), Pydantic automatically validates that 
   the body matches our strict schemas:
   ```python
   class ConfigPayload(BaseModel):
       name: str
       keywords: Dict[str, float]
   ```
   If a client sends malformed JSON, FastAPI automatically rejects it with a 
   detailed HTTP 422 error, without developers writing boilerplate validation code.
3. Speed:
   FastAPI is built on top of Starlette and Pydantic, making it one of the 
   fastest Python frameworks available—rivaling the performance of Go and Node.js.
4. Auto-Generated Documentation:
   FastAPI automatically generates interactive OpenAPI/Swagger documentations at 
   `/docs` and `/redoc`, facilitating testing.

Why not Flask?
--------------
Flask is synchronous by default. Handling multiple file uploads and long-polling 
connections simultaneously in Flask requires multi-threading configurations, 
which are prone to memory bloat. Furthermore, Flask lacks built-in input 
validation, meaning developers must write manual parsing code or install multiple 
third-party libraries (like Marshmallow and Flask-RESTful), creating fragmented, 
hard-to-maintain codebases.

6. EXPLAINABLE AI (XAI): HOW SHAP (SHAPLEY ADDITIVE EXPLANATIONS) WORKS
================================================================================

Explainable AI is the cornerstone of judicial machine learning. Black-box models 
cannot legally be used to prioritize court cases. CaseTriage resolves this 
by integrating SHAP.

How SHAP Works Mathematically:
------------------------------
SHAP is based on cooperative game theory (specifically Shapley Values, formulated 
by Lloyd Shapley). It frames the model prediction as a "game" where the payout 
is the model's prediction minus its average prediction, and the "players" are 
the engineered features.

1. Base Value (Expected Value): The average prediction of the model across the 
   entire training dataset. For CaseTriage, the base value is roughly ~55.00 points.
2. Marginal Contribution: For any feature (e.g., "Criminal Base"), SHAP calculates 
   the difference in model prediction when that feature is included versus when 
   it is excluded, evaluated across all possible combinations of other features.
3. Additive Feature Attribution: The final prediction is the sum of the base value 
   plus the SHAP values of all features:
   
   Prediction = Base Value + SHAP_Criminal + SHAP_Family + SHAP_Keywords + SHAP_Precedent + SHAP_TextLen

Implementation in judge.py:
----------------------------
```python
ml_model = joblib.load("priority_model.pkl")
explainer = shap.TreeExplainer(ml_model)  # Optimized Tree Explainer

features = extract_features(new_case, raw_distances, active_keywords)
ml_score = float(ml_model.predict([features])[0])
shap_values = explainer.shap_values([features])[0] # Compute Shapley values
```

Our system maps these shapley values to UI representations:
- Positive impact (red): Added points (e.g. "Criminal Base" adds 12.5 points 
  because the case involves violence).
- Negative impact (blue/gray): Subtracted points (e.g. "Precedent Match" is -3.1 
  because a highly similar precedent was already solved, reducing urgency).

7. RULE ENGINE: KEYWORD INGESTION, SCORING, AND DYNAMIC CONFIGS
================================================================================

CaseTriage utilizes a dual-engine architecture:
- Heuristic Rule Engine (rule_engine.py)
- Machine Learning Engine (priority_model.pkl)

The Rule Engine operates as follows:
1. Base Points: Every case begins with a base score of 25.0 points.
2. Case Type Weight:
   - If case_type is "criminal": +22.0 points.
   - If case_type is "family": +15.0 points.
3. Keyword Matching: The engine scans the lowercased summary text against the 
   combined keyword-weight dictionary.
4. Safety Cap: The total points accumulated from keywords is strictly capped 
   at +32.0 points. This acts as a critical security control to prevent malicious 
   users from inflating case urgency via keyword stuffing (repeating words like 
   "murder" multiple times).
5. Precedent Adjustment: If ChromaDB finds a similar case with a distance < 0.9, 
   the engine adds +12.0 points.

Dynamic Configurations:
-----------------------
When the API boots up, it reads system_config.json, which stores admin-defined 
keyword profiles. The API bridge handles the activation, deactivation, or creation 
of these profiles.
When judge.py processes a case:
- It fetches the immutable `BASE_URGENCY_KEYWORDS` dictionary (e.g. "bail": 10, "rape": 15).
- It reads system_config.json.
- For all active configs (e.g. "Extreme Fraud Weights" profile), it merges their 
  keyword weights onto the base dictionary.
- The scoring uses this merged dictionary, applying adjustments in real-time.

8. RESOLUTION OF SORTING COLLISIONS: DETERMINISTIC JITTER
================================================================================

In a database containing thousands of cases, multiple dockets can yield identical 
raw priority scores (e.g., both evaluate to exactly 84.00). This causes unstable 
sorting in database queries and UI components, making it difficult for court 
clerks to know which case to address first.

CaseTriage solves this through a Deterministic Jitter calculation:
```python
unique_hash = int(hashlib.md5(case_id.encode()).hexdigest(), 16)
text_len = len(new_case.get("summary", ""))
decimal_modifier = ((unique_hash % 89) + (text_len % 10)) / 100.0
final_score = raw_final + decimal_modifier
```

Why it is Deterministic:
-------------------------
We do not use random numbers (`random.random()`). A random modifier would change 
every time a query is executed, causing cases to shift positions on refresh. 
By seeding the modifier with the MD5 hash of the unique `case_id` and the length 
of the summary, the jitter is completely deterministic. A specific case will 
always receive the exact same modifier (e.g. +0.73), resulting in a stable, 
consistent priority queue.

9. PRECEDENT SURFACING: DENSE VECTOR EMBEDDINGS & CHROMADB
================================================================================

To assist clerks, CaseTriage locates historical precedents using a local Vector 
Database (ChromaDB) and dense vector embeddings.

1. Embedding Generation: We use SentenceTransformers' `all-MiniLM-L6-v2` model. 
   This model maps raw English legal summaries into a 384-dimensional dense 
   vector space. Words or sentences with similar semantic meanings are placed 
   close to one another in this high-dimensional space.
2. Indexing: Precedent cases are stored in ChromaDB (chroma_db_storage/).
3. Querying: When a new case is ingested, its summary is embedded and passed 
   to ChromaDB to perform a cosine distance query.
4. Self-Excluding Search Filter:
   If we query ChromaDB for the closest match, and that same case is already 
   indexed, the query will return that exact case as the #1 match (distance ≈ 0.00).
   To prevent the system from surfacing the case itself, judge.py queries `n_results=2`.
   If the distance of the first result is less than 0.05 (indicating a duplicate 
   or the same case), the engine selects the second closest match:
   ```python
   match_idx = 1 if len(distances_1d) > 1 and distances_1d[0] < 0.05 else 0
   ```
   This ensures a true historical precedent is surfaced.

10. CONTAINERIZATION WITH DOCKER: HOW IT HELPS SOLVE ML DEPENDENCIES
================================================================================

What is Docker?
---------------
Docker is a tool that allows developers to package an application with all of 
its dependencies (such as runtime engines, environment libraries, and system files) 
into a standardized unit called a Container.

Why Docker is Crucial in this Project:
--------------------------------------
Machine learning libraries are notoriously difficult to set up consistently 
across operating systems. Specifically:
- XGBoost, ChromaDB, and PyTorch (underlying SentenceTransformers) require 
  system-level C++ compilers (`build-essential`) and shared libraries (like `libgomp.so` 
  for multi-threading).
- Running the code directly on Windows might fail if the user lacks these C++ 
  build dependencies, or on Mac if CPU architecture mismatches.

Our `Dockerfile.backend` solves this by standardizing the build environment:
```dockerfile
FROM python:3.11-slim
WORKDIR /app
RUN apt-get update && apt-get install -y \
    build-essential \
    libgomp1 \
    && rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
```
This guarantees that regardless of whether the host system is Windows, Mac, or 
Linux, the application runs inside an isolated Debian container with `libgomp1` 
and `build-essential` preinstalled, avoiding dependency mismatches.

Docker Compose:
---------------
Our `docker-compose.yml` links the three micro-services (API, Watchdog, Frontend) 
together. It mounts the project files via volumes (`.:/app`), allowing you to edit 
code locally and see changes propagate in real-time inside the running containers.

11. CLOUD DEPLOYMENT STRATEGIES: RENDER VS. VERCEL (THE SERVERLESS DILEMMA)
================================================================================

Deploying a multi-process, stateful machine learning system requires careful 
architecture. Let's compare Render and Vercel:

DEPLOYING ON RENDER (Highly Recommended for Backend & State)
-----------------------------------------------------------
Render is a PaaS (Platform as a Service) that supports long-running processes, 
Docker containers, and persistent disk mounts.

1. Deploying the Backend (FastAPI + Watchdog):
   - You can deploy our backend using the existing `Dockerfile.backend`.
   - Render allows you to deploy a "Web Service" for the FastAPI bridge.
   - Persistent Disk Mount: This is critical. Render containers are ephemeral 
     (rebooting clears local files). Since our Vector DB (ChromaDB), queue 
     (`master_queue.txt`), configurations (`system_config.json`), and logs 
     (`system_logs.txt`) are stored locally, you MUST mount a Persistent Disk 
     in Render (e.g., at `/app/data` or `/app/chroma_db_storage`) to prevent 
     losing scored cases and database indices.
   - Dual Process Execution: Render charge per service. To avoid paying for two 
     separate services (one Web Service for API, one Background Worker for Watchdog), 
     you can use a startup shell script (`run.sh`) in your Docker container:
     ```bash
     #!/bin/bash
     python watchdog-orchestrator.py &
     uvicorn api_bridge:app --host 0.0.0.0 --port 8000
     ```
     This executes both processes concurrently inside a single Render service.

2. Deploying the Frontend (React Vite Dashboard):
   - Deploy as a "Static Site" on Render. Connect your GitHub repository, set 
     the build command to `npm run build` (inside the `dashboard` directory), 
     and the publish directory to `dashboard/dist`. This is free and fast.

DEPLOYING ON VERCEL (Best for Frontend; Serverless Constraints for Backend)
--------------------------------------------------------------------------
Vercel is designed for frontend hosting and serverless functions (Next.js, Vite).

1. Deploying the Frontend:
   - Import your GitHub repo. Vercel automatically detects Vite/React.
   - Set the root directory to `dashboard` and deploy. Vercel deploys this 
     globally to edge servers.

2. The Serverless Dilemma for Backend Deployment:
   - Vercel is *Serverless*. This means it executes API requests via ephemeral 
     functions (AWS Lambda under the hood) that spin up, handle a request, and 
     immediately shut down.
   - Ephemeral Filesystem: Vercel serverless functions have a read-only 
     filesystem with only a tiny writeable `/tmp` directory. You CANNOT write 
     to `master_queue.txt`, `system_config.json`, or local ChromaDB storage. 
     Any local changes are destroyed within seconds.
   - No Background Running: You cannot run `watchdog-orchestrator.py`. Vercel 
     does not support long-running listeners or directory watchers.
   - Cold Start & Latency: SentenceTransformers and XGBoost models are heavy. 
     Loading them on a cold start in a serverless function can take 10+ seconds, 
     violating Vercel execution limits.

How to adapt CaseTriage for a Vercel-only Backend (Serverless Transition):
--------------------------------------------------------------------------
If you MUST run the backend on Vercel, you have to transition away from local 
files:
- Databases: Move the queue from a text file (`master_queue.txt`) to a hosted 
  relational/NoSQL database (like MongoDB Atlas, PostgreSQL, or Supabase).
- Vector DB: Replace the local ChromaDB with a cloud-hosted vector service 
  (like Pinecone, Qdrant Cloud, or Chroma Cloud).
- Ingestion Queue: Replace the Watchdog with a message broker queue (such as 
  SQS, RabbitMQ, or BullMQ). When a case is uploaded, a background serverless 
  task is pushed to the queue for execution.

Summary Recommendation:
-----------------------
- Deploy the React Frontend (`dashboard`) to Vercel (for high-speed global load).
- Deploy the Backend API & Watchdog container to Render as a Web Service (with 
  a Persistent Disk mounted for storage). This keeps the local file-based database 
  system working perfectly without rewriting code.
