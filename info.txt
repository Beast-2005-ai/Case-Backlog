PART 1: NON-TECHNICAL OVERVIEW & VALUE PROPOSITION
================================================================================

1. DESCRIPTION & MISSION
CaseTriage is an enterprise-grade, full-stack orchestration system designed 
to automate the triage, classification, and prioritization of massive legal 
casework backlogs. Instead of relying on manual sorting, CaseTriage utilizes 
a dual-engine AI approach. It ingests raw legal dockets, categorizes them by 
region (US, India, International) and law type, and scores their urgency 
using both a dynamic heuristic rule engine and a trained XGBoost Machine 
Learning model.

2. PROBLEMS SOLVED
* Manual Triage Bottlenecks: Judicial systems are overwhelmed. Human clerks can 
  only read a limited number of cases per day, leading to compounding delays.
* Subjective Prioritization: Human triage is inherently inconsistent; different 
  clerks assign different priorities to similar dockets based on subjective bias.
* Black-Box AI Dilemma: Conventional machine learning models assign urgency scores 
  without explanation. In legal settings, this violates basic rights of auditability 
  and judicial transparency.
* Jurisdictional Nuances: Legal systems are regionally siloed. Standard software 
  cannot parse and prioritize dockets from different countries (e.g., US vs. 
  Indian law) without custom programming.
* Downtime Recovery: When administrative systems go offline, dockets pile up, 
  causing severe processing spikes when reconnected.

3. ADVANTAGES OVER TRADITIONAL SYSTEMS
* 85% Triage Time Reduction: Processes cases in 1.8 seconds on average (50+ cases 
  per minute throughput) compared to hours/days manually.
* Judicial Auditability: Provides a mathematical breakdown of why the AI assigned 
  a priority score, ensuring transparency.
* Zero-Downtime Rule Tuning: Non-technical administrators can adjust custom urgency 
  keyword weights from a UI dashboard on-the-fly, with immediate application.
* Highly Resilient: Continues to accept case submissions during background worker 
  downtime and runs an automated batch triage scan ("Backlog Crusher") upon reboot.

PART 2: USER EXPERIENCE & CORE FUNCTIONALITIES
================================================================================

* Intelligent Triage Queue: Ranks cases dynamically from 1 to 100 based on legal 
  urgency. Allows instant regional filtering (US, India, International) and search.

  display a SHAP waterfall chart. This visualizes exactly how many priority points 
  were added or subtracted by specific features (e.g., Criminal Base, Keyword 
  Density, Text Complexity).
* Precedent Surfacing Panel: Displays the closest historical legal precedent 
  surfaced by the local vector database, showing similarity distances and facts.
* Dynamic Config Dashboard: Allows admins to create custom scoring profiles 
  (e.g., "Extreme Fraud Weights") that stack additively onto the base dictionary.
* Print-Ready PDF Reports: Renders docket summaries, priority scores, and SHAP 
  charts into high-quality PDFs with a single click.

PART 3: CORE TECHNICAL ARCHITECTURE & DATA FLOW
================================================================================

CaseTriage utilizes a modular, microservices-style pipeline consisting of a React 
Frontend, a FastAPI API Bridge, a background Python Watchdog, a local ChromaDB 
vector database, and an XGBoost ML Regressor.

[Data Source] ──► [UI / Folder Drop] ──► [API Ingestion] ──► [Watchdog Triage]
                                                                  │
  ┌───────────────────────────────────────────────────────────────┘
  ▼
[ChromaDB Vector Match] ──► [Heuristic Score] ─┐
                                               ├──► [Composite Score] ──► [SHAP Explainer]
[XGBoost Feature Prep]   ──► [ML Score]        ─┘         │
                                                          ▼
                                                   [MD5 Jitter Modifier]
                                                          │
                                                          ▼
                                                [Append master_queue.txt]

--------------------------------------------------------------------------------
PHASE 1: INGESTION, FILTERS & NLP ROUTING
--------------------------------------------------------------------------------
1. Ingestion Entry Points:
   - Direct UI Upload: FastAPI API (api_bridge.py) accepts files.
   - Bulk Folder Drop: Direct files dropped into pending_cases_json/.
2. Content Validation & Safeguards:
   - Word Count Filter: Files with fewer than 20 words are rejected immediately.
   - Duplicate Blocker: Scans active files to prevent redundant ingestion.
3. NLP Region Detection:
   - Scans text for regional indicators:
     * Keywords: "IPC", "CrPC", "Delhi", "Maharashtra", etc. ──► Routed to /Indian
     * Keywords: "SCOTUS", "Texas", "Federal", "Circuit", etc. ──► Routed to /US
     * If neither are found, routed to /International.
4. Categorization:
   - Maps keyword triggers to legal domains (e.g., "murder" -> Criminal; 
     "divorce" -> Family; "patent" -> Corporate/IP).
5. Standardization:
   - Wraps raw dockets into uniform JSON structures, assigns UUIDs (e.g., US-UPLOAD-2026-A1B2), 
     and writes them to the pending_cases_json/ regional subdirectories.

--------------------------------------------------------------------------------
PHASE 2: THE HEURISTIC RULE ENGINE (rule_engine.py)
--------------------------------------------------------------------------------
Heuristically evaluates cases based on text search and metadata tags.
* Base Score: 25.0 points.
* Case Type Weight:
  - If type contains "criminal": +22.0 points.
  - If type contains "family": +15.0 points.
* Keyword Density Weight:
  - Matches case summaries against the active configuration dictionary (e.g., "murder": 15, "rape": 15, "fraud": 5).
  - Multiplier is capped at a maximum of +32.0 points to prevent keyword stuffing.
* Precedent Weight:
  - If the semantic precedent distance returned by ChromaDB is < 0.9: +12.0 points.
* Total Possible Rule Score: ranges from 25.0 to 91.0 points.

--------------------------------------------------------------------------------
PHASE 3: FEATURE ENGINEERING & MACHINE LEARNING PIPELINE
--------------------------------------------------------------------------------
1. Training (train-model.py):
   - Historical cases are compiled and baseline-scored using the rule engine.
   - Five numerical features are engineered and fed into an XGBoost Regressor model.
   - The serialized model is outputted as priority_model.pkl.
2. Feature Extractor (feature_engineering.py):
   Transforms raw case JSON text into a 5-dimensional numerical array:
   - Feature 0 [Criminal Base]: 1 if case_type contains "criminal", else 0.
   - Feature 1 [Family Base]: 1 if case_type contains "family", else 0.
   - Feature 2 [Keyword Density]: Sum of active keyword weights matched in text (capped at 32).
   - Feature 3 [Precedent Match]: Similarity score (1.0 - Cosine Distance) of closest precedent.
   - Feature 4 [Text Complexity]: Length of the summary text (character count).
3. XGBoost Model (priority_model.pkl):
   - Hyperparameters: max_depth=6, n_estimators=100, learning_rate=0.1.
   - Outputs a predicted regression score (ML Score) representing priority.

--------------------------------------------------------------------------------
PHASE 4: VECTOR DATABASE & PRECEDENT SURFACING
--------------------------------------------------------------------------------
* Embedding Engine: SentenceTransformers ("all-MiniLM-L6-v2") maps docket summaries 
  into dense vector embeddings (384 dimensions) on GPU/CPU.
* Vector DB: ChromaDB (stored locally in chroma_db_storage/) performs cosine similarity searches.
* Self-Excluding Search Filter:
  - Query requests n_results=2.
  - If the closest returned result has a distance of < 0.05 (indicating it matched 
    the input case itself or a direct duplicate), it shifts index to return the second 
    closest document. This guarantees a true historical precedent is retrieved.

--------------------------------------------------------------------------------
PHASE 5: DUAL-ENGINE TRIAGE & DETERMINISTIC JITTER (judge.py)
--------------------------------------------------------------------------------
* Composite Score Calculation:
  - Final Priority Score = (0.4 * Heuristic Rule Score) + (0.6 * ML XGBoost Score).
  - The final score is hard-capped at a maximum value of 99.99.
* Sorting Collision Resolution (Deterministic Jitter):
  - To prevent identical scores (which disrupt queue sorting), the system injects a jitter:
    decimal_modifier = ((md5_hash(case_id) % 89) + (len(summary) % 10)) / 100.0
  - Added to the raw score, this ensures a unique decimal offset (e.g., 84.73 vs 84.12) 
    that ranks cases deterministically without changing the semantic score.
* Explainable AI (SHAP Explainer):
  - A shap.TreeExplainer processes the engineered features against the XGBoost model.
  - Decomposes the score into Shapley values, mapping positive and negative point 
    contributions to specific features (e.g., "Criminal Base: +12.50", "Precedent Match: -3.10").
  - Outputs a structured XAI_DATA JSON string appended to the queue database.

--------------------------------------------------------------------------------
PHASE 6: ASYNCHRONOUS EVENT MONITORING & RESILIENCE
--------------------------------------------------------------------------------
* Background Agent (watchdog-orchestrator.py):
  - Monitors the pending_cases_json/ folder recursively.
  - On file creation, it triggers judge.py asynchronously.
  - Idle Efficiency: Polling runs on a 3-second sleep loop, consuming minimal CPU.
* The Backlog Crusher (Downtime Recovery):
  - When the orchestrator reboots, it compares pending folder contents against master_queue.txt.
  - Finds all files created while the orchestrator was offline (which the API saved in 
    "Pending" status with a base score).
  - Batch-processes them through the AI judge before returning to live standby.

================================================================================
PART 6: CODEBASE DIRECTORY & FILE MANIFEST
================================================================================

* /pending_cases_json/ : Directory monitored by Watchdog; dockets are routed into:
  - /US : US law keyword dockets.
  - /Indian : Indian law keyword dockets.
  - /International : General fallback dockets.
* /chroma_db_storage/ : Storage directory for ChromaDB vector indexes.
* api_bridge.py : FastAPI server connecting React to the backend. Handles uploads, logs, 
  and system configurations.
* watchdog-orchestrator.py : Directory monitor; coordinates backlog sweeps and live scoring.
* judge.py : Core logic runner; fetches precedents, extracts features, calculates rule/ML scores, 
  generates SHAP values, applies jitter, and updates master_queue.txt.
* rule_engine.py : Evaluates base points, case type weights, keyword scores, and precedent weights.
* feature_engineering.py : Extracts the 5-dimensional numerical array from case text.
* train-model.py : Trains the XGBoost Regressor model and serializes it to priority_model.pkl.
* priority_model.pkl : Serialized XGBoost Regressor ML model file.
* system_config.json : Configuration database containing active administrator profiles and keywords.
* master_queue.txt : Text-based priority queue database storing scored case JSON objects.
* system_logs.txt : Text file capturing runtime audit trails streamed by the UI terminal.
* patent.md : Drafted Invention Disclosure Form for university incubation center submission.
* Annexure.md : Prior-art patent search report comparing CaseTriage to existing patents.
* requirements.txt : Python dependency list.
